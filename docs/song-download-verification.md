## 独立审阅与修正

进行一次独立、只读的全分支审阅；随后一次修正流程，覆盖了全部 9 项发现，无暂缓小问题。删除竞争条件保留 Critical 等级；编码重试、命名、编码索引、后台响应和退出清理保持 Important；容量显示和多选计数按用户在 TF 卡与批量删除场景中的实际影响提升为 Important。

回归测试均实际观察失败，再修正并跑完整测试：

1. 确认后替换文件或父目录：删除操作先隔离实际文件、重新校验，再用目录句柄删除或移动到回收站，保留替换文件。
2. TF 卡的 UTF-8 重试：本地与重新确认的位置共用 `retry_confirmed`，确认位置后仍应用 UTF-8 决策。端到端测试验证两种位置最终成功。
3. 编号或歌单顺序改变：保存请求的基础文件名，改变编号后生成新副本。
4. 仅歌词的带点号名称：只剥离完整输出后缀，新增音频保持同名关联。
5. 部分 GBK 输出成功后 UTF-8 重试：每个歌词文件分别记录编码，不把已有 GBK 文件算作 UTF-8。重新扫描保留已核对文件的编码；未知外部编码不复用。
6. 慢速文件刷新：磁盘检查在全局状态锁之外执行，核对快照后短暂更新状态；测试验证取消和快照不会等文件检查结束。
7. 退出与临时音频：后台等待工作线程停止，最长 20 秒；启动时清理已登记且目录身份一致的工作文件，保留未知文件。关闭窗口会等待，隐藏到后台仍保留原有行为。
8. 切换保存目录：清除旧容量显示并重新读取，过期结果不覆盖新目录。
9. 单独勾选歌曲：立即更新选择计数。

## 实现中的判断及代价

按执行顺序记录全部判断：

1. 提前在 API 任务引入 `futures-lite`，因为流式测试需要执行器；代价仅为依赖提交次序变化。
2. 使用已授权的直接测试命令替代任务记录包装器，因为包装器中的沙箱不能监听本地 TCP；相同覆盖范围，代价是执行记录方式不同。
3. 使用 GStreamer pbutils 探测媒体，避免维护自制探测器；代价是新增编译与运行依赖。
4. 歌单目录总是附加 ID，避免同名碰撞；代价是目录名稍长。
5. 进度事件仅携带当前任务，目录或终态变化仍发送完整快照；代价是维护两种事件形式。
6. 增加资源查询接口供本地媒体验收使用，流式下载、转换和文件管理仍是正式实现；代价是一个小型内部接口的维护。
7. 格式化原有 Rust 文件以通过整体格式检查；代价是审阅中额外的空白变动。
8. 用目录句柄实现 [Freedesktop Trash](https://specifications.freedesktop.org/trash/latest/) 移动与恢复信息，替代会重新打开路径的 GIO 删除；代价是回收站实现的维护，安全权限不支持时会保留原文件并报告失败。
9. 未用用户账号验收实际歌曲下载，以本地响应和媒体服务验证；代价是线上接口变化仍可能需要调整。
10. 未使用物理 TF 卡，通过临时目录验证身份、失效、确认和重试；代价是硬件及 FAT/exFAT 挂载细节尚未实测。
11. 独立审阅没有重新审阅未改变的上游依赖实现，只审查新增下载接口与集成；代价是仍可能继承上游问题。

## 用户实测后的线上修复

2026-10-05，用户两次下载两首歌曲均显示完成 0 / 2。只读下载记录确认四个任务均在获取资源阶段报 `Cannot verify the song duration`，尚未开始写入音频。上游歌曲详情查询把 `c` 参数生成成带多余反斜杠的非法 JSON，导致时长查询失败。

修复使用 JSON 序列化器生成歌曲 ID 对象数组；回归测试覆盖复现的两个超过 32 位有符号整数范围的 ID 及空列表，实际经历失败再通过。该修复同时适用于完整歌单的歌曲详情读取。

线上验证：匿名状态下，两首歌的时长查询已经成功，但播放和下载均无完整资源。随后只读加载软件已有登录文件，使用正式资源获取、流式传输、MP3 准备及完整性校验代码，在自动清理的临时目录验证两首歌成功：

- `3422762511`：7,237,621 字节，301,531 毫秒。
- `3411982875`：5,949,738 字节，247,902 毫秒。

两者均为完整音频、MP3 固定 192 kbps、44.1 kHz、双声道。测试未修改登录文件、用户下载记录或用户选择的保存目录，也未输出登录凭据或资源地址。默认完整测试不访问音乐服务，线上测试需显式执行并提供登录文件路径。补充了上游来源文件中的本地修改说明。

## 重复下载提示修复

2026-10-05，用户反馈已保存歌曲重复提交只提示“加入下载队列：1”，随后没有结果提示。原因是提交提示直接统计返回的任务 ID 数量，其中包含已保存跳过的任务及已有活动任务；全部跳过时没有活动任务，也不会触发批次结束通知。

入队时在原有去重判断处记录新排队、已保存跳过、已有活动任务及歌单缺失详情的数量，提交提示只显示对应非零项。保留原生底部提示样式和旧入队接口；状态统计与实际去重使用同一锁下的结果，避免后台完成或并发提交造成误报。新增四项回归测试覆盖已保存歌曲、活动任务、混合歌单和补齐歌词，并验证实际通知文本及中文翻译。已观察旧行为下计数与提示测试失败，修复后通过。

## 整张歌单数量校验修复

2026-10-05，用户点击 DOUDOU 歌单顶部下载按钮时提示 `Cannot verify all playlist tracks`。只读线上复现发现，同一接口返回 29 个曲目 ID，`trackCount` 却是 28；旧的相等判断拒绝了这张清单。

数量校验改为“实际 ID 清单不少于声明数量”。多出的曲目全部保留，仍拒绝数量不足的清单；顺序、重复 ID 去重和缺失歌曲详情的处理沿用已有流程。回归测试先在旧实现下失败，修复后证明 29 个 ID / 声明 28 的情况会保留全部 29 首；原有不完整清单和超过 1000 首的测试继续通过。

显式线上测试已读取这张实际歌单的全部 29 首，重复项为 0，29 首歌曲详情均成功获取。测试只读登录文件和歌单，不创建用户下载任务、不修改歌单；本次验证覆盖整单枚举，音频传输沿用之前已验证的单曲和本地批量下载实现。更新设计记录中的数量判据，并为线上歌单验证保留需显式提供登录文件、歌单 ID 和期望数量的忽略测试。
